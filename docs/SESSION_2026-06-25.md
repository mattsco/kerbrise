## Ce que l'inspection a révélé (corrige le review, qui ne lisait que le code)

Le backend est PLUS mûr que ce que le review supposait :
- `check_booking_overlap()` existait déjà (le review le croyait absent) — sémantique
  pivot correcte, exclut les cancelled. MAIS non atomique → d'où la migration 0002.
- `prevent_non_admin_sensitive_update` ferme déjà l'escalade de privilèges sur `users`
  (is_admin, is_family_head, family_id, email). Le risque §3.2 est en réalité couvert.
- `reset_approvals_on_date_change` gère finement inclusion vs débordement de période.
- Toutes les fonctions ont `SET search_path` (bonne hygiène SECURITY DEFINER).
- 20 policies RLS cohérentes, 11 triggers, 6 fonctions — tous NON versionnés.

Défaut métier trouvé et corrigé (0001) : `update_booking_status_after_approval`
comptait `count(*)` des lignes approved au lieu de `count(distinct family_id)`,
sans contrainte unique sur `approvals(booking_id, family_id)`.

## Pour committer depuis le Mac

```bash
# depuis la racine du repo kerbrise
rm -f .git/index.lock .git/HEAD.lock   # locks résiduels du sandbox
git add db/migrations/ lib/ components/ app/
git commit -m "db: contraintes versionnées 0007-0010 + gestion UI 23505/23P01 + refacto data layer bookings"
git push
```

NB : ces 3 migrations sont DÉJÀ appliquées en prod. Les committer ne les ré-exécute
pas (sauf si tu lances `supabase db push` sur un environnement vierge). Elles servent
de trace versionnée, pas de script à rejouer sur la prod actuelle.
